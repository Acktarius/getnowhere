Packaged desktop identity

Operator brief — change packaged-desktop-identity

TL;DR

The installed desktop app currently pretends to be "Alice", the throwaway identity we invented for running two copies side by side during development. That name is stamped on the log output, the window title, and the folder holding the user's wallet. Along with it, the app ships a fixed, documented local network port and a shared password that is the same on every machine in the world.

After this change an installed app has no development identity at all, and the private channel it opens on the user's own machine is different every single time it starts — different port, different password, no traces left behind.

What you'll get

  • Launching the installed app prints [desktop], not [desktop:alice].
  • The window is titled simply "Get Now Here", with no role or debug tag.
  • User data lives in ~/.config/getnowhere instead of ~/.config/getnowhere-desktop-alice.
  • Each launch opens its private local channel on a port the operating system picks at random, so there is no fixed number for anything else to look for.
  • The app learns that port through a private message from the networking process, not by reading a log line.
  • Each launch generates a fresh random password for that channel, and never writes it to a temporary file the way it does today.
  • The installed app always starts its own networking process and will never latch onto one it did not start.
  • Only one installed copy can run at a time, so the wallet folder is never opened by two processes. A second launch focuses the first window.
  • If the main app is killed hard, the networking process exits too, so it does not keep talking on the mesh by itself.
  • Running the app the developer way — npm run desktop:alice and desktop:bob — behaves exactly as it does now.

How it works

Today one setting controls eleven different things, and it quietly falls back to "alice" whenever nobody says otherwise. Installed builds never say otherwise. The fix moves that whole decision into one small, testable piece of code that asks a single question first: is this an installed app, or a developer running from source? Installed builds simply do not participate in the developer identity, and they ignore the developer's environment switches so the leak cannot happen again through a side door.

For the local channel, the app asks the operating system for any free port. The networking process reports that port over a private IPC channel, and only then does the app connect. Installed builds also take a single-instance lock on the profile folder — random ports stop TCP collisions, but without the lock two copies would still share the wallet database. The networking process watches for its parent and exits if the main app dies without a clean shutdown. 

flowchart TD
    A[App starts] --> B{Installed, or run from source?}
    B -- Installed --> C[No role. Storage in ~/.config/getnowhere]
    C --> L[Single-instance lock on profile]
    L --> E[Start own networking process on any free port]
    E --> F[IPC: process replies with the port it got]
    F --> G[Connect using a fresh random password]
    B -- From source --> D[Alice or Bob. Storage per role]
    D --> H[Fixed port 7901, shared password, may join an existing process]

What changes for you

  • No new commands. Your development workflow is untouched.
  • After installing the new build, the app starts empty — see the warning below.
  • Old data can be removed with rm -rf ~/.config/getnowhere-desktop-alice ~/.config/getnowhere-desktop-bob.
  • If you ever need a specific port for troubleshooting, setting HOLEPUNCH_PORT still forces one.
Data loss is intentional here. Everything the desktop app remembers — the encrypted wallet, contacts, and the keys for existing chat rooms — is stored inside the folder named after "alice". Renaming that folder means installed builds start clean. You accepted this because the project is still in testing, and because writing a migration tool would be the only part of this work that touches a folder containing a wallet. Anyone who already created a wallet in an installed build needs their recovery phrase.

Risks and open questions

RiskHow it's handled
Existing installed users lose access to their wallet Called out in the release notes; the recovery phrase is the way back
The app waits forever for the networking process to report its port The wait is time-limited on the IPC message; on timeout startup fails clearly
Two installed copies corrupt the wallet folder Single-instance lock after the profile path is set; second launch focuses the first
Networking process survives a hard kill of the main app Sidecar watches parent death and exits, tearing down the mesh
The developer Alice/Bob setup breaks by accident Tests assert today's exact values for both roles and both modes
Final confirmation needs a real desktop The installed-app check is a manual step at the end; the networking half runs automatically

Out of scope

  • No migration tool, and no attempt to move or rescue existing data.
  • Installed builds are single-instance; only the developer Alice/Bob harness still runs two copies.
  • No change to how two people actually find and talk to each other, and no change to the encryption layers.
  • No change to the web or mobile builds.
