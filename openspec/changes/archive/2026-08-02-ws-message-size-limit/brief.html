Cap WebSocket bridge message size

TL;DR

Today a local client can shove an enormous WebSocket frame at Holepunch and force a heavy parse and peer fan-out. After this change, oversized messages get a coded error and the socket is closed — and every bridge error carries a stable code documented under docs/. Normal chat sizes keep working unchanged.

What you'll get

  • Whole inbound WS messages capped (default ~264 KiB with wrapper room).
  • Chat frame payloads capped at 256 KiB (same sealed-frame budget as peer NDJSON).
  • Two separate config knobs so you can retune wrapper vs payload independently.
  • Abusive clients get one coded error, then disconnect (close code 1009).
  • A documented bridge error map (docs/architecture/holepunch-bridge-errors.md) covering size and existing protocol errors.

How it works

flowchart TD
  A[WS client sends message] --> B{Raw bytes over max?}
  B -->|yes| E["error code message_too_large then close"]
  B -->|no| C[Parse JSON]
  C --> D{frame payload over max?}
  D -->|yes| F["error code payload_too_large then close"]
  D -->|no| G[Handle / fan-out as today]

What changes for you

  • No UI change for normal sealed chat frames.
  • Limits live in Holepunch config.json if you need to retune later.
  • Clients should switch on error code; human message remains for logs.
  • A buggy client that exceeds the limit will see the bridge drop and may need to reconnect.

Risks and open questions

  • Anything that truly needs payloads larger than 256 KiB will need a config bump or a different media path.
  • The WebSocket library may hit the size ceiling before our handler — we still emit a coded error on the close path when possible.

Out of scope

  • UI reconnect polish after a forced close.
  • Bridge auth token work and peer hello hardening (separate findings).
  • Changing the existing Hyperswarm NDJSON line cap.
