Live chat: counters that never repeat and never get stuck

TL;DR

Live (peer-to-peer) chat can break permanently in two ways today. A phone killed at the wrong moment can forget how many messages it encrypted and reuse an encryption nonce. A device that missed more than 64 of its contact's frames can never read another one until the chat is re-invited. This change puts the message counter on the wire so a receiver always catches up, and makes the phone save its counters before anything leaves the device.

What you'll get

  • A chat that is stuck in "crypto mismatch" today reconnects on its own once both devices run the new build. No re-invite needed.
  • Missing any number of frames (flaky network, contact offline, many retries) no longer breaks the chat.
  • Killing the Android or iOS app mid-chat can no longer cause an encryption nonce to repeat or old frames to be accepted again.
  • If the phone cannot save its counter, the message is not sent and you see a send error, instead of silently sending an unsafe frame.
  • The same frame arriving twice (two network paths) is accepted only once.

How it works

Each encrypted frame now starts with a version byte and the sender's message counter. The receiver rebuilds the nonce from that counter, and accepts the frame if the counter is not older than what it has already seen and the encryption tag checks. The nonce is built the way TLS 1.3 builds it (a fixed per-session value mixed with the counter), so two counters can never share a nonce. The counter is also covered by the tag, so changing it breaks the frame.

sequenceDiagram
  participant A as Sender
  participant S as Secure storage
  participant B as Receiver
  A->>A: encrypt with counter N
  A->>S: save counter N+1 and wait
  S-->>A: saved (or error: stop, no send)
  A->>B: frame = version, N, ciphertext
  B->>B: N below what I have seen? drop
  B->>B: rebuild nonce from N, check tag
  B->>S: save receive counter N+1 and wait
  B->>B: show message

This design was checked by an external review (Perplexity, acting as a cryptography reviewer). Four of its points were adopted: the TLS-style nonce, the counter in the authenticated data, one-at-a-time receive per chat, and a hard stop before the counter could ever overflow.

What changes for you

  • Both devices must be updated together. An old build cannot read frames from the new build, and the reverse is also true. Ship desktop and mobile at the same time.
  • Existing chats keep working after the update. Keys and history are unchanged.
  • On mobile, every live frame now waits for one secure-storage write, which adds a few milliseconds.

Risks and open questions

RiskHandling
A device on the old build cannot chat with one on the new buildAccepted. Release both together.
A frame that arrives out of order over a second network path is droppedSame as today. Each connection keeps order.
A crash between saving the receive counter and showing the message loses that messageThe existing resend-after-reconnect usually brings it back. Documented.
The phone's secure storage never answers a counter writeThe wait is capped (5 s) and counts as a failed write: the message is not sent, instead of the chat freezing.
A contact deliberately sending a huge counterOnly your authenticated contact can do this, and they could simply stop answering anyway. No cap, because a cap would bring back the stuck state.

Out of scope

  • Automatic new keys (rekeying) or a resync handshake.
  • Clearer connection-status labels ("waiting for contact", "online"). That is a separate change right after this one.
  • Delivery receipts, and chain-relay (L1′) behaviour.
