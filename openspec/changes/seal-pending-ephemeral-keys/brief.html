Seal pending invite ephemerals

Change brief — for operator approval (SEC-2026-006)

TL;DR

While a chat invite is waiting to finish, the app currently parks a one-time private key in ordinary app storage as readable text. After this change that key lives only inside the encrypted wallet, and is deleted when the room is done — including leave / revoke — so overnight invites still work without leaving plaintext secrets on disk.

What you'll get

  • Send / Accept invite still works after phone off or app kill (until accept window ends).
  • No plaintext invite private keys in browser or prefs KV.
  • Keys cleared after successful connect handoff, decline, abandon, expiry cleanup, and leave/revoke.
  • Old plaintext leftovers migrated into the wallet once, then deleted.

How it works

Alice (or Bob) still keeps a temporary key in memory while the wallet is open. For survival across restarts, a copy is saved inside the same encrypted wallet file you already unlock with your password (on phones, the Keystore-backed wallet file). When the invite finishes or the room is destroyed, that copy is removed.

  User->>App: Send or Accept invite
  App->>App: Keep key in memory
  App->>WalletBlob: Save pending key (sealed)
  Note over App,WalletBlob: Phone off OK
  User->>App: Unlock later / peer accepts
  WalletBlob->>App: Restore key
  App->>App: Finish session handoff
  App->>WalletBlob: Delete pending key
  Note over App: Leave or revoke also deletes

What changes for you

  • No new screens or settings.
  • Same invite UX; safer storage underneath.
  • If you somehow still had an in-flight invite from an older build, the next unlock migrates it automatically.

Risks and open questions

  • If the wallet fails to finish saving before a hard kill, a brand-new invite might still need a resend (same class of risk as other wallet writes).
  • While the wallet is unlocked, in-memory keys can still be read by compromised UI code — this fix is about at-rest plaintext storage.

Out of scope

  • Restore-wallet weak password issue (separate finding).
  • Accept-after-expiry, misnamed “encrypt” helpers, register spam gate.
  • Changing how Hyperswarm topics are derived on the wire.
