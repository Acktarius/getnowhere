Stop leaking chat room topics over Holepunch

TL;DR

Today, if you have two chat rooms open, a peer who only belongs in room A can learn the secret address of room B from the Holepunch sidecar. After this change, the sidecar only treats a peer as present on topics Hyperswarm already says you share — it never advertises your full room list on the wire.

What you'll get

  • No more broadcasting every joined room’s topic to every peer connection.
  • A peer invited only to room A cannot learn room B’s discovery topic from hello messages.
  • Forged “hello, I’m on topic B” messages cannot fake peer presence on B.
  • Docs match reality: invite already carries the topic; Holepunch only rendezvous.

How it works

Alice and Bob already know the room topic from the invite. Both join that topic on Hyperswarm. The sidecar counts a remote peer only when Hyperswarm reports the shared topic on that connection. It stops sending (and stops trusting) app-level hello messages that listed every local topic. 

Invite (SmartMessage) → both know topicRef
        ↓
Each side joins topic on Hyperswarm
        ↓
Connection + shared topic events → peer count
        ✗  (removed) NDJSON hello of all local topics

What changes for you

No new UI or invite flow. Sidecar behavior and docs change under the hood. If Holepunch peer counting is slightly slower on rare inbound paths, chain / SmartMessage fallback remains the safety net — same product story as today when discovery is slow.

Risks and open questions

  • Inbound connections sometimes start with no topic list from Hyperswarm; we rely on later topic events instead of hello.
  • Manual check still useful: Alice in A+B, Eve only in A — Eve must never see B’s topic on the wire.

Out of scope

  • Changing how topicRef is derived from room / relationship ids.
  • Changing post-connect crypto proof or L3 encryption.
  • Redesigning SmartMessage invite / L1′ fallback.
