iOS notification permission chain

TL;DR

On iPhone the app never asks for notification permission, so it never gets a push token, never registers for wake, and nobody can wake it. Every step fails silently. After this change, turning on a notification setting really asks iOS, waits for your answer, and either turns the switch on (and registers for wake) or leaves it off with a one-line explanation right under it.

What you'll get

  • Tapping Notifications, Wake contact or Notification banner shows the iOS (or Android) permission prompt when needed.
  • A switch only shows on when the feature actually works: permission granted, alerts allowed, and (for Wake contact on iPhone) the wake server accepted the registration.
  • When it can't turn on, the switch stays off and a message appears directly under it — no dialog. It disappears when you leave Settings:
    • Notifications need to be turned on in Settings → Apps → Get NowHere → Notifications.
    • Notifications are not available in this build.
    • Wake registration failed. Check your connection and try again.
  • Opening Settings shows the real state: a switch saved as on without the matching phone permission shows off, so the next tap asks again.
  • The app's own notification handler runs from launch (foreground notifications show as a badge only).
  • The end-to-end check also hits the live wake servers: both health endpoints, plus a poke to a random handle that must arrive through ntfy as wake. A silent server outage now fails the check.

How it works

Today the app sends "please ask for permission" into the native layer and never hears back. The change turns that into a question with an answer: the native shell asks the phone, waits for the user's choice, fetches the push token only if allowed, and replies to the app screen. Settings then decides whether the switch may turn on.

sequenceDiagram
  participant U as User
  participant S as Settings screen
  participant N as Native shell
  participant OS as iOS
  participant G as Wake server
  U->>S: tap Wake contact
  S->>N: ask permission (alerts + token)
  N->>OS: request authorization
  OS-->>U: system prompt
  U-->>OS: Allow / Don't Allow
  OS-->>N: answer
  alt allowed
    N->>OS: get push token
    N-->>S: authorized + token
    S->>G: register token
    G-->>S: wake handle (or error)
    S-->>U: switch on (or off + message)
  else denied / unavailable
    N-->>S: denied or unavailable
    S-->>U: switch off + message under it
  end

What changes for you

  • No new screens. The three existing switches behave honestly and explain failures.
  • If you already had a switch "on" from an older build, it will show off the first time you open Settings — tap it once to get the prompt.
  • The wake server README gains an operator note about the 2026-11-18 outage (a Docker upgrade left ntfy and the gateway stopped for five days) and the guard against it.
  • You run one paid adhoc-ios build and a two-person wake test on it.

Risks and open questions

  • The exact iOS root cause is still unconfirmed. This change makes it visible: "not available in this build" means the native part is not loading; a working prompt means the old silent flow was the bug.
  • If the ad-hoc build installs but two users on it still get no wake notification, we switch to the fallback (let the Expo notifications library own iOS permissions).
  • If iOS ever reports "provisional" permission, the badge switch accepts it, but Wake contact and banners require full permission with alerts on.

Out of scope

  • Tapping a notification does not yet open the matching room.
  • No changes to the chat protocol, encryption, invite format, or the wake server's API.
  • No TestFlight or App Store build until the ad-hoc test passes.
